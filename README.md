# SF Day-Tripper

**Pitch:** A one-page trip planner that turns Overture Maps' San Francisco places into a personalized, geographically sane day-by-day itinerary — pick your pace, dietary needs, interests, and how you're getting around, and get a route instead of a list.

## Why this idea

Most "AI itinerary" tools are a chat prompt that returns prose. The actual hard part isn't generating suggestions — it's making sure a day's stops are geographically close enough to be walkable (or transit/car-reachable) and roughly ordered so you're not zigzagging across the city. That's a real, scoped engineering problem Overture's place + coordinate data can genuinely solve, so this app leans entirely on structured geo-clustering rather than an LLM free-text response.

## How it works

1. **Data**: `data/extract_places.py` pulls ~50k SF places from Overture (bbox around SF city limits, `type=place`), keeps only entries with `confidence >= 0.5` and a name, and buckets each into one of 5 categories (Food & Drink, Parks & Recreation, Arts & Sights, Shopping, Everything else) using Overture's own top-level taxonomy hierarchy. Output is one flat `places_sf.geojson` (~13MB), loaded into memory at server startup — no database.
2. **Clustering**: for an N-day trip, places matching the selected interests are split into N geographic clusters via a small hand-rolled k-means (lat/lon). Each cluster becomes one day.
3. **Scheduling**: within a day, stops are picked and ordered greedily starting from the day's start time — breakfast first, then nearest attractions, with a coffee break worked in mid-morning and lunch worked in once the clock passes noon (filtered by food style, if any). Each stop gets an estimated visit duration by category (a heuristic — see Cuts) and a travel time to the next stop based on straight-line distance and transport mode; the day stops adding stops once it would run past the end time.
4. **Transport mode** sets both the search radius for food stops (walking ≈1.2km, transit ≈3km, car ≈8km) and the assumed travel speed between stops (walking 4.5km/h, transit 15km/h, car 22km/h) — it does not currently bias toward actual transit lines (see Cuts).
5. **"Where are you staying?"**: an optional neighborhood picker (hand-curated approximate coordinates, not from Overture). If set, day clusters are ordered by distance from that point (nearest = Day 1, exploring further out on later days), and breakfast each day is anchored near the stay location rather than near that day's cluster — matching how a trip actually starts from a hotel/Airbnb. Each day's route is also drawn starting and ending at that point on the map.
6. **Up to 2 landmark "highlights" per day**: bridges (verified `category == "bridge"` at confidence ≥0.95) plus 5 individually-verified famous SF sights matched by exact name — Coit Tower, Palace of Fine Arts, Ferry Building, Twin Peaks, Pier 39 — preferred over an equally-close generic business or a shopping stop. See Cuts for why this list is short and hand-picked rather than broader, and for real bugs found while building it.
7. **No repeats across the trip**: place selection is trip-wide, not per-day — a spot used on Day 1 (breakfast, a landmark, anything) is excluded from every later day, so a 5-day trip doesn't recommend the same bridge or coffee shop twice.
8. **Cuisines (multi-select)**: checkboxes for 11 cuisines with real presence in SF (Chinese 321, Mexican 300, Italian 235, ... — checked against the actual extract; e.g. "British" exists as a category but only has 3 entries city-wide, too sparse to offer). A day now has both a lunch and a dinner slot; if more than one cuisine is selected, dinner actively avoids repeating whatever cuisine lunch used that day, falling back to the same one only if nothing else is nearby. Dietary restriction (food style) still takes priority over cuisine if the combination would leave nothing nearby. Meal triggers are adaptive to the day window, not fixed clock times — see Cuts.
9. **Distance/time summary**: each day shows total walking (or transit/driving) distance and time getting between stops, summed from the same haversine + travel-time math used to build the schedule.

## Stack

FastAPI (Python) backend serving a static vanilla-JS + Leaflet frontend from the same process — one deployable service, no build step, no API keys (OpenStreetMap tiles).

## Key trade-offs & cuts

- **No opening hours, no prices, no ratings.** Overture's Places schema doesn't include them — the itinerary intentionally doesn't fake those numbers.
- **Visit duration is an estimate, not measured data.** Overture doesn't record how long a visit takes, so each stop gets a duration from a hand-picked table by category (museum ~90min, landmark ~20min, coffee ~20min, restaurant ~60min, etc.), scaled by pace. It's a reasonable heuristic, not a fact — stated plainly rather than implied as precise.
- **Food style filtering is real, not guessed.** Overture's category taxonomy has actual `vegetarian_restaurant`, `vegan_restaurant`, `halal_restaurant`, `kosher_restaurant`, `gluten_free_restaurant` categories — confirmed against the SF extract (37 halal, 59 vegetarian, 28 vegan, etc.) before building the feature. It's applied to the day's main meal (lunch); breakfast/coffee spots aren't filtered by diet since Overture doesn't tag cafes that way.
- **"Public transit" mode is a radius heuristic, not real transit routing.** Overture has transit line _geometry_ (I confirmed SF's Muni rail lines are present) but no GTFS schedule data — no stop times, no trip planning. Doing that properly means pulling in SFMTA's separate GTFS feed, which felt like scope creep away from what Overture itself provides. Left as a clearly-labeled v2.
- **Distances are haversine (straight-line), not real street/walking routes.** Good enough for clustering and rough ordering at city scale; not turn-by-turn directions.
- **Group size / kids-or-elderly toggle** were part of the original brainstorm but cut — they'd only ever adjust the same pace/stops-per-day knob already exposed directly, so a separate input would've been redundant complexity.
- **No popularity/review data exists in Overture, and I tried a category-based proxy for it — then reverted most of it.** Places has no ratings or review counts at all, so "famous landmark" can only be approximated from category tags. I initially mapped `landmark_and_historical_building` / `monument` / `national_park` to a "notable sight" boost, but testing surfaced real problems in the underlying data: those tags are also applied to ordinary historic apartment buildings, an embassy, and — more surprisingly — several records literally named "Yosemite National Park" and "Half Dome Yosemite Park" geotagged in downtown San Francisco (bad crowd-sourced entries that pass the confidence filter). Confidence score turned out to be a data-quality signal, not a popularity one, so it doesn't separate these from the real thing. I narrowed the feature to just `category == "bridge"` at confidence ≥ 0.95, which cleanly catches Golden Gate/Bay Bridge without the noise, deduped near-duplicate records of the same physical bridge (multiple ~identical "Golden Gate Bridge" entries a few meters apart) within 300m, and capped it to one landmark visit per day so duplicates spread across the bridge's length don't turn a day into a bridge tour. This is a real limitation of the data, not a feature I could fully deliver — stated plainly rather than papered over.
- **Residual noise in Arts & Sights beyond the bridge fix, left as-is.** `landmark_and_historical_building` (the same tag from the point above) is still the primary category for ordinary apartment buildings and office addresses in this dataset, and it's Arts & Sights' single largest category (600+ entries in SF) — so itineraries with that interest selected will occasionally surface a building that isn't actually a sight. I chose not to strip the whole category (it also correctly tags real landmarks), and a per-entry cleanup pass is out of scope here. Worth knowing about rather than presenting the bucket as cleaner than it is.
- **Tried and cut: an Outdoor/Indoor "setting" filter.** Built it on verified category lists (`park`, `hiking_trail` for outdoor; `museum`, `cinema` for indoor), confirmed it worked correctly end-to-end — but decided the underlying category data isn't trustworthy enough across the board to ship as a real filter (same root issue as the landmark noise above: Overture's crowd-sourced tagging is inconsistent enough that a confident indoor/outdoor claim would sometimes just be wrong). Removed rather than keep a feature that looks precise but occasionally lies.
- **Meal timing is adaptive, not fixed-clock, because a fixed trigger broke.** Dinner originally triggered strictly "after 6pm." A single long visit (e.g. a 120min museum) could jump the clock straight from before 6pm to near the day's end in one step, skipping the trigger entirely and leaving no dinner. Fixed by triggering lunch/dinner early once there's ~2.5 hours left before the day ends, in addition to the normal clock trigger — whichever comes first. Found via a 540-combination parameter sweep, not by inspection.
- **Famous-sight list is 5 names, hand-verified, not a broader search.** Checked Palace of Fine Arts, Twin Peaks, Coit Tower, Pier 39, Alcatraz, Lombard Street, Ferry Building, Ghirardelli Square individually. A plain name search is *worse* than the category noise from the point above — "Twin Peaks" the hill shares its name with "Twin Peaks Auto Care," "Twin Peaks Tavern," "Twin Peaks Pizza and Pasta" (none the actual hill) — so each of the 5 kept names was checked against its exact category and confidence before inclusion, not just string-matched. Alcatraz is dropped even though a clean "Alcatraz Island" (museum, conf 0.92) entry exists: it's boat-only, and none of this app's transport modes reach it, so recommending it would be a dead end. Lombard Street has no POI entry at all — it's a road, not a place, so it lives in Overture's separate Transportation theme, outside a Places-only extraction.
- **Two more real bugs found while verifying the famous-sight list, both fixed.** (1) Two literal "Golden Gate Bridge" records existed 1.7km apart — exact-name dedup was originally scoped to only the curated famous-name list, so it missed this since bridges qualify via a separate category rule. Extended exact-name dedup to *all* landmarks, not just the curated list. (2) A mislabeled `"Golen Gate Bridge San Francisco"` record (category "bridge", confidence 0.97) turned out to have coordinates 165m from Pier 39 — nowhere near the real bridge — and because it had higher confidence, the radius-based dedup pass silently ate Pier 39 as its "duplicate," even though they're unrelated places. Fixed by scoping radius dedup to only compare entries of the *same category* (a mislabeled bridge can now only collide with another bridge, never with an amusement park).
- **A care facility was recommended for dinner — a name-based safety filter, not a category one.** Found "Sunset Care Home Inc" and "Alcoholics Rehabilitation Association" both mislabeled by Overture's own source data with primary category `restaurant` at 0.95+ confidence — nothing in the category signal distinguishes them from a real restaurant. This matters more than typical category noise because `food_drink` is *always* in the meal candidate pool regardless of what interests are selected. Added a narrow name-based denylist (`care home`, `assisted living`, `hospice`, `rehab`, etc.) scoped specifically to the food_drink bucket, since that's the acute failure mode found — not a general-purpose content filter.
- **The "Landmark" display badge used to trust the same noisy category text it shouldn't have.** The frontend was labeling any stop whose category matched `/landmark|historical|monument/` as "🗽 Landmark" for display — which is exactly the unreliable `landmark_and_historical_building` tag already known to mislabel apartment buildings (a user caught "Mt. Sutro Apartments" showing this badge). Fixed by exposing the backend's verified `is_landmark` flag in the API response and using *that* for the badge, not a text match — so the label now only ever appears on the curated bridge/famous-sight set, never on an arbitrary category string.
- **Shopping bucket curated down from 6,440 to 1,487 places.** Checked real category counts and found "Shopping" dominated by everyday retail — `grocery_store` (409), `clothing_store` (385), `furniture_store` (230), `pharmacy`, `hardware_store`, `cosmetic_and_beauty_supplies` (89) — not tourist shopping. There's also no `shopping_mall` category in this dataset at all; SF's actual malls are tagged `shopping_center` or `department_store` instead. Reassigned the non-touristy categories out of the Shopping bucket at extraction time rather than trying to filter them at runtime.
- **Landmark cap raised from 1/day to 2/day, and a real bug found doing it.** With only ~10 landmarks city-wide, capping at one was needlessly conservative. Raising it uncovered two real bugs: (1) the boost radius was measured from the last-visited stop, which drifts — chaining from one landmark to the next-nearest could walk clear across the city (Golden Gate Bridge → Bay Bridge → 4th Street Bridge in one day); fixed by measuring from the day's fixed cluster centroid instead. (2) Even centroid-anchored, a diffuse cluster (no stay-location set) could still put multiple distant landmarks within radius of the same centroid; fixed with a small hard cap (2/day) on top of the radius check. Shopping-bucket stops are also now deprioritized below any other available attraction — only picked once nothing else nearby fits, addressing the actual product complaint (shopping crowding out real sights) directly rather than just as a side effect of the landmark fix.

## Running locally

```
python3 -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt
python data/extract_places.py   # one-time; writes data/places_sf.geojson
uvicorn backend.main:app --reload --port 8000   # run from the repo root
```

Then open http://localhost:8000.

## Deploying (Render)

`data/places_sf.geojson` is committed to the repo, so the build doesn't need to re-run the
Overture extraction (slow, and depends on external data availability) — it just installs deps
and serves the file that's already there.

- Build command: `pip install -r requirements.txt`
- Start command: `uvicorn backend.main:app --host 0.0.0.0 --port $PORT`

Only re-run `python data/extract_places.py` locally when you want to refresh the data, then
commit the updated `places_sf.geojson`.
